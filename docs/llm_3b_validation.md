# 3B：可选 LLM 适配与验证

## 1. Business Problem

商家自然表达不一定符合原固定句式。可选模型把请求转换为受限意图与参数，再由原业务系统决定可查询什么、还缺哪些信息、能否准备草稿。政策解释只使用本次可信检索证据，不让模型替数据库宣称操作成功。

## 2. Architecture Decision

沿用已确认的 HTTPX 简单适配方案，不新增依赖或厂商 SDK。Model Adapter（模型适配层）负责把内部输入转换为约定的模型 HTTP 格式，并把上游失败收敛为安全错误，不负责业务执行。

协议采用 messages 请求、choices[0].message.content 字符串 JSON 响应。地址、模型和密钥由服务端配置；默认关闭。单次请求无自动重试、无重定向、限制响应大小，不允许请求正文或模型输出配置上游地址。CLI 不配置时仍只依赖标准库。

结构校验使用标准库：拒绝重复 JSON 键、未知意图、未知字段、错误类型、非法枚举、畸形 ID、非有限数。每个意图有自己的 Slots 白名单，模型无确认、取消、退款、权限或任意函数执行入口。

保留服务端自己的当前任务。传给理解模型的只有当前请求和任务类型、状态、业务 Slots、缺参名单，不发送身份、授权快照、确认哈希或全部对话历史。任务关联订单若已失权，不发送上下文。通知补参使用 notification_edit，它仅调用已有 update_slots，不新增主要业务写操作。

生成器返回简短解释、source_id、连续原文 quote。编号与文件/版本/页码由服务端保留和生成，虚假来源、错配引文或模型故障退回原文。返回前再次校验授权、有效期、目录及文件哈希。

## 4. Implementation Evidence

```text
CLI / HTTP → 原可信身份与 Session / Workspace 校验
→ 加载原 Task Context → 校验关联订单权限
→ 离线规则或可注入 ModelUnderstanding
→ 结构 / 意图 / Slots 白名单 / 自评分门槛
→ 原确定性 Router
Query → 原订单、通知、工单服务 → SQLite
Action → 原参数收集 / 草稿 → 独立确认 → 原重验 / 事务 / 回执
Knowledge → 原权限及版本过滤 → Dense + BM25 + RRF + Rerank
→ 无证据或检索故障时不调用生成器
→ EvidenceGenerator → source_id 与原文匹配 → 再校验权限及来源
→ 模型解释与真实引用，或原文摘录回退
```

核心入口：conversation/model.py、conversation/understanding.py、merchant_support.py、knowledge/generation.py、knowledge/retrieval.py。api/app.py 与 merchant_demo.py 只负责可选配置和客户端生命周期。

没有修改通知、订单、工单服务的核心事务机制、数据库结构、HTTP 确认契约或业务写操作数量。未安装依赖，pyproject.toml 和 uv.lock 本轮未调整。

## 6. Real Bug / Failure Case

**实际环境故障：**初次全量测试中，运行环境禁止 Milvus Lite 绑定 127.0.0.1 临时端口，导致三处集成初始化失败。日志明确为 Operation not permitted。获准本地测试运行权限后，同一实现完整通过；未更换数据库或依赖。该问题是本地运行权限，不是模型效果或云端故障。

**静态发现并补测：**原订单查询只判断 Slots 是否为空；模型可能只提取 shop_id，缺 order_id。现改为检查必填字段，返回缺参而非调用错误。通知查询同样逐项检查缺参；已有事务不改。

恶意模型输出、超时、错引文等属于主动注入的验收场景，不包装成真实模型线上事故。

## 7. Trade-off

保持原串行协调锁，模型推理会增加同实例的请求等待，不作并发性能承诺。模型超时只有在原离线规则明确识别时才回退业务路由，不能以故障为理由猜动作；原始问题始终用于知识权限过滤。

confidence 0.65 为启发式自评分门槛，未校准，不是安全概率。合法 Slots 也可能由模型误提取；服务端权限、展示及确认限制执行风险，但真实识别质量需后续测量。

引用结构、source_id 和 quote 可验证，不等于语义忠实性已得到证明。模型可能使用真实引用给出错误解释；当前保留原文对照，真实模型阶段须独立评测。未引入第二个判分模型或额外框架来伪装已经解决该问题。

## 8. Current Boundary

已实现：可配置 HTTP 模型适配、受限意图/参数识别、可选证据生成、显式启用开关、离线与摘录回退、替身测试及原接口兼容。

未验收：真实厂商协议兼容、实际模型识别/忠实性、真实调用成本和时延、云端 Milvus 服务。

下一步：用户确认使用云服务器自行部署的 Milvus；先完成本阶段，再单独确认迁移方案。Multi-Agent 实现的只读复用检查如下，不代表已经迁移。

明确不做：真实模型或付费请求、新依赖、修改事务核心、前端、真实电商平台、外部身份系统、Git commit/push。

重点掌握：P0 模型建议与服务端执行授权分离；P0 引用可追溯与语义正确是不同保证；P1 显式启用、可复现替身与真实模型验收的区别。

## 云端 Milvus 复用只读结论

检查来源为 talent-eval-agents/backend/app/milvus_store.py、evidence_index_service.py、hybrid_search_service.py、test_milvus_store.py 与 pyproject.toml。未读取真实 .env，也未连接云端。

可复用思路：MilvusClient(uri, token) 注入；集合结构/维度检查；Dense 与 BM25 的同范围过滤；RRFRanker；版本不可用时拒绝自动改旧集合；可注入客户端便于替身验证。

不能原样复用：候选人 candidate_id、tenant_id/permission_scope 字段、人才文档关系、既有 collection、数据内容和权限语义。客服应使用独立 collection，保留 Workspace/店铺范围、生效时间、文件哈希和引用校验。

兼容性缺口：人才项目约束 PyMilvus >=2.6,<2.7，客服当前为 3.0.2；服务端实际版本、分词器、索引类型和 SDK 行为尚未云端核对。客服本地 Embedding 为 512 维，不能直接沿用其他模型生成的向量。后续以最小连接适配复用，不复制整个人才服务层或建立共享框架。
