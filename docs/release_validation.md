# 3C / 3D 最终本地验收（2026-11-07）

## 结论与业务能力

本地可演示、可复现的商家售后链路已完成：政策咨询 → 授权订单查询 → 工单补参/准备 → 显式确认 → 事务创建/回执 → 工单状态查询。保留通知修改、任务修订/取消/恢复/结果核对，具有 CLI 和 HTTP 两种入口。RAG 使用真实本地模型，LLM 生成/理解适配只做替身验收。尚不能宣称生产上线、真实模型或云端验收。

业务代码本轮没有更改；新增评测工具、12 条探索性样本和报告，更新文档与权重忽略规则。没有新增依赖、迁移云端或改索引。架构图、API 示例及复现步骤见 README。

## 最终验证

**Level 1：**CPython 3.14.7 / macOS Apple Silicon；`SAAS_LLM_ENABLED=0 HF_HUB_OFFLINE=1 SAAS_RAG_INTEGRATION=1 PYTHONPATH=src .venv/bin/python -B -m unittest discover -s tests -v`，**120 项全部通过，无跳过，21.165 秒**。包含此前跳过的 8 项真实本地检索集成，以及 3A 最后调整的 409 错误映射。模型替身为 MockTransport/FakeModel，不发生真实生成式模型调用。

本轮实际 HTTP 使用本机 TCP、随机临时端口、临时合成 SQLite 与已有只读本地索引。确认工单后直接查询数据库，工单、订单关联、回执各 1 条；服务和临时数据已清理。模型首次准备依赖外网；本轮推理没有下载模型或调用外部 API。

## 检索质量

**Level 2，小规模合成离线评测。** 原 24 条问答和 6 条边界不修改，模型快照和索引保持不变。新增 12 条样本是在观察失败后设计的探索性诊断集，不是盲测集。Recall@5 为每题找回标注证据比例再平均；Hit@1 为首位属于标注证据的题数。检索耗时含查询 Embedding，不含权限查询、模型加载和 HTTP。

| 原 24 题 | Recall@5 | Hit@1 | P50 | P95 |
|---|---:|---:|---:|---:|
| Dense | 91.67% | 21/24 | 7.52 ms | 15.18 ms |
| 混合 RRF | 91.67% | 22/24 | 6.89 ms | 10.46 ms |
| 混合 + Rerank | 100% | 23/24 | 845.08 ms | 1245.10 ms |

| 新增 12 题 | Recall@5 | Hit@1 |
|---|---:|---:|
| Dense | 100% | 11/12 |
| 混合 RRF | 100% | 10/12 |
| 混合 + Rerank | 100% | 11/12 |

6/6 原边界符合预期且不返回引用。以上不预设混合检索一定优于纯向量，也不把小样本结果当生产泛化指标。

### 实际回答与证据门槛

当前服务只取重排前 3 条、分数 >= 0 的证据。因此离线 Recall@5 高不等于成功返回答案。

| 样本 | answered | no_evidence | 返回全部标注证据 |
|---|---:|---:|---:|
| 原始 24 题 | 19 | 5 | 19 |
| 探索性 12 题 | 12 | 0 | 11 |

原集 5 条已知有答案问题被保守回退；探针“收到货八天了，现在想退货应该怎么办？”仅返回退货期限，没有返回标注的超期条款。不能用 100% Recall 隐藏漏答/证据不足。未降低阈值追求满分，因为可能增加不相关证据输出；后续需更多正负例共同校准。

## “签收八天”问题分析

查询：签收都八天了，还能让客服看一下吗？目标 returns:2.0:2（超期退货）。

- Dense：目标第 6；首位退货期限。
- BM25：目标第 6；首位退货期限。
- RRF：目标仍第 6。融合没有获得任何一路的首位支持。
- Rerank：目标升到第 5；前面依次为破损、缺凭证、期限、店铺材料。目标原始分数 -4.5031，首位 -2.8363，均低于服务当前 0 门槛。真实 Knowledge 响应为 no_evidence，不是输出首位破损政策。

解释属于基于排名和文本的推断：句子包含签收和时间，但没有显式“退货/超期”；知识条款未以“八天”表达超期，当前检索/重排没有稳定完成“八天 > 示例七天”的关系判断。不是向量库漏存条款或权限误过滤。

最小实验：只在重排输入中加入现有章节标题，索引和原文件不变。原集首位命中从 23/24 降到 22/24，新集保持 11/12，目标问题仍错误。**拒绝将该实验应用到正式检索**。未硬编码天数或单条句式，未改模型、索引或引入新框架。

## HTTP 延迟与共享锁

**Level 1，本机运行，热模型。** 知识和普通查询各 10 次，锁竞争 5 次；P95 为排序后的 nearest-rank，小样本结果仅供定位。

| 场景 | P50 | P95 |
|---|---:|---:|
| HTTP + 离线识别 + 真实 RAG | 727.02 ms | 794.94 ms |
| HTTP 订单查询，独立运行 | 6.39 ms | 17.87 ms |
| 另一 Session 已进入重排时查询订单 | 690.02 ms | 731.34 ms |

五请求“政策→订单→准备→确认→查状态”耗时 714.17 ms；不含用户思考时间、模型加载和真实 LLM。与检索评测耗时不是同一批调用，不能相减推算固定接口开销。

MerchantSupport 共享 RLock 覆盖整个 handle；重排在锁内，故不同 Session 的订单查询也会等。计时在真实 scores() 开始时发出查询，无人工 sleep 延长重排。此次不拆锁，避免改变待办展示与确认的一致性；接受本机演示并发限制。若后续要服务多人，再设计将慢检索移出锁并在返回时重新校验上下文/授权，不以删除锁作为修复。
