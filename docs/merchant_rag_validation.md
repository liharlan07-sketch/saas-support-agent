# 第二阶段：商家政策检索验收

## 1. 业务问题

商家咨询超期退货时，需要知道当前可用条款和出处。搜索结果不能把旧版本或未授权店铺的政策当作现行依据；没找到证据时，不编造政策或替人工批准工单。

## 2. 架构决定

按已确认方案保留单进程商家客服。默认入口不加载可选依赖；`--rag` 注入 Knowledge Support。使用 Milvus Lite 3.2.2、PyMilvus 3.0.2、中文 BGE 512 维模型、INT8 BGE 重排及原文摘录。生成式回答未接入。Markdown 按标题、文本型 PDF 按页切分，扫描件不纳入此版。

## 3. 实现与验证归属

用户确认依赖、边界、验收顺序并授权本地运行；Codex 实现、执行兼容性验证、测试和评测。未将 Codex 操作记录为用户亲自实现或独立验证。

## 4. 调用链与代码入口

```text
版本目录 → 原始 Markdown / PDF → 带文件哈希、版本、章节/页码的片段
→ 真实本地 Embedding + Milvus 中文 BM25 → 重开校验 → 发布快照
商家输入 → 原离线意图路由 → policy_query
→ SQLite 查有效成员及店铺授权 → 日期/版本/范围生成允许的片段 ID
→ Milvus Dense 与 BM25 同范围召回 → RRF 合并
→ 本地模型重排 → 再校验授权、目录及来源哈希
→ 返回原文摘录和可定位引用；无证据与索引/模型故障分别处理
原订单查询 → 准备工单 → 显式确认 → 原事务及回执 → 状态回查
```

- `knowledge/models.py`：固定模型快照、校验权重和离线推理。
- `knowledge/policies.py`：解析、切分和目录校验。
- `knowledge/retrieval.py`：快照发布、权限过滤、检索、重排和引用。
- `merchant_support.py`：知识分支注入，原写入路径不改。
- `knowledge/evaluation.py`：同一标注集下的检索对比。

## 5. 实测证据

2026-11-06，Codex 使用 macOS Apple Silicon、CPython 3.14.7、本地锁定依赖和两份校验通过的权重执行。17 个索引片段含旧版、未来版和不可见店铺；评测固定到 2026-11-06，24 条有答案问题另加 6 条边界问题。所有政策、身份、订单和工单均为合成演示数据。

**Level 1：**86 项测试通过（原 80 项 + 6 项真实 Milvus/模型集成）。原命令行用 Python `-S` 禁用第三方包后仍跑通。启用检索的原命令行演示引用 `returns-v2.md` 超期退货条款，随后读取订单、写入已确认的工单和回执，并查回待人工受理。集成测试还实际解析并引用了 PDF 第 1 页。依赖锁的离线一致性检查通过。

**Level 2：**相同查询、语料、范围与 10 个候选，预热后计检索耗时，包含向量计算、不含模型初始化和业务权限查询。证据 Recall@5 表示每题前 5 条找回的标注证据比例，再取平均；Hit@1 指首条是标注证据的问题数。

| 模式 | Recall@5 | Hit@1 | 中位耗时 | P95 耗时 |
|---|---:|---:|---:|---:|
| Dense | 91.67% | 21/24 | 5.84 ms | 6.50 ms |
| Dense + BM25 + RRF | 91.67% | 22/24 | 6.38 ms | 6.94 ms |
| 混合召回 + Rerank | 100.00% | 23/24 | 684.81 ms | 782.40 ms |

重排候选数为 3、5、10 时，前 5 个样本的检索中位耗时分别为 207.86、338.08、696.13 ms；这一组只测延迟，不推断不同候选数的准确率。模型加载约 1.57 s（含权重校验）；评测进程峰值常驻内存 1,115,127,808 字节，约 1.04 GiB，不含其他进程。6/6 边界样本符合预期（3 个无证据、3 个无权访问），没有输出引用。详见[原始报告](merchant_rag_eval_2026-11-06.json)与 [README 复现步骤](../README.md#可选本地政策检索)。

## 6. 失败场景

- **实际故障：**系统直连 Hugging Face 超时；默认下载缓存曾写入受限目录。将缓存放在项目内，使用系统代理从固定官方地址分段读取，最后核对完整 SHA-256。未替换模型或引入镜像。
- **实际误排：**“签收都八天了，还能让客服看一下吗？”三种方式首条都不是正确的超期条款，重排首位为商品破损。前 5 条找到了正确证据，不能把首位错误当作已解决。
- **测试覆盖：**两路均过滤未授权店铺、过期版及未来版；检索期间撤权不返回证据。注入模型及索引验收故障，故障不回退到静态条款，未验证的新索引不替换旧指针。目录或原文件变更后拒绝旧引用。

## 7. 取舍

此小样本上混合召回改善了一个首位命中，没有提高 Recall@5；重排提高了这两项，但开销明显。保留 10 个候选用于当前交付，不能仅凭延迟决定缩减候选；后续可在独立验证集上一起比较质量和时延。

## 8. 当前边界

验收只覆盖本地单进程和合成政策。重排分数门槛是启发式规则，不是已校准的置信度；24 条标注问答不代表生产效果。没有真实生成式模型、平台、API 服务、扫描件解析、多进程索引或生产压力测试。现有示例文档中的店铺范围由客服入口校验，不是操作系统文件访问控制。
